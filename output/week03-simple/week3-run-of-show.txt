WEEK 3 — FROM LOCAL VERSION CONTROL TO WORKING TOGETHER
Two-hour run of show

Start with lessons/week03_github-desktop/1_github_basics.md beside Desktop or
GitHub, then move to 2_project_repo.md for team collaboration. Students can
read the first guide on GitHub until we update their local copies. Slides are backup
reference. Demonstrate a few actions, let students repeat them, then ask the
checkpoint. The stash/conflict exercise stays in the first guide.

BEFORE CLASS

On the work computer, use the current course repository files. Check that the
interactive opens and has its basic, branch/PR, and conflict scenarios. Have
Desktop signed in and VS Code ready. Prepare a practice repo for your demo.
Use a fresh name if week3-practice already exists; do not delete old work.

Rehearse part 3's next-step.md exercise in a personal practice repo: start with
the same committed and pushed sentence, save a local replacement without
committing, and commit a different replacement on GitHub. Pull should stop;
stash and pull, then restore to trigger the conflict. Start class with a clean
practice repo and no existing stash. The interactive is the fallback.

For the later team conflict, both teammates must branch from the SAME version
of team-next-step.md. Open both PRs before merging the first. Use the lesson's
exact one-line edits so the second PR reliably conflicts.

0:00–0:05 — INTERACTIVE PREVIEW (guide part 1)

Open How Git Thinks. Use only Save, commit, push, pull. Ask which copy changes
before each click. Introduce the names Git, GitHub, and GitHub Desktop briefly.
Then move straight into the real app.

0:05–0:20 — LOCAL VERSION CONTROL (part 2)

Create a local week3-practice repository with a README. Do not publish yet.
Edit and save; read the diff; commit; inspect History. Students make a second
small edit and commit. Show a useful message rather than "changes".

Check: "Where are the commits? Can anyone see them on GitHub yet?"
Explain Markdown while editing: a heading, a paragraph, a list, and a link.
Keep the emphasis on files and history on their own computer.

0:20–0:45 — PUBLISH, PUSH, PULL, AND A DELIBERATE CONFLICT (part 3)

Publish that SAME repository through Desktop. It creates and connects the
GitHub copy. Show the rendered README and history in the browser.
Make another local commit. Refresh GitHub before pushing, then push and refresh.

Briefly show avatar → profile/repositories/account settings, versus Settings
inside a repository. Make a small README edit on GitHub and commit it there.
Fetch in Desktop; the local file is still old. Pull; now the change appears.
Explain that we will use this to update the teaching repository after the
stash/conflict exercise.

Check: "Maya committed; can Luis see it? Luis pushed; why is Maya's file old?"

Reserve the final 10–12 minutes for the planned stash/conflict exercise.
Everyone creates next-step.md with "Next step: choose a data source.", commits,
and pushes. Locally replace it with "Next step: compare two data sources."
and SAVE WITHOUT COMMITTING. In the browser replace the original line with
"Next step: check the data license." and commit on main.

Fetch and pull: the warning should appear. Explain what it protects, stash,
and pull. Inspect the online sentence now present locally, then restore the
stash. Read both conflicting versions. Agree on "Next step: compare two data
sources and check their licenses.", remove the conflict markers, save, commit,
and push. Verify the final sentence on GitHub before clearing any leftover
exercise stash. The blocked pull and the later conflict are different moments.

0:45–0:50 — GET THIS WEEK'S COURSE FILES (end of part 3)

Apply what students just practised to the updates they need every week. Save
open files, select the existing compss-211a repository in Desktop, and check
main and the teaching repository URL. Inspect local Changes, fetch, and check
for local commits waiting to be pushed before pulling.

Students with no local work can pull the updates and open the local Week 3
guide. Help students with unfinished notebook edits use stash, pull, and
restore as appropriate, then check their work. Already committed changes need
help reconciling histories; stashing does not set those commits aside. Keep
students' work intact. They can continue reading the guide on GitHub while
receiving help. Check the updated local files and History.

0:50–1:00 — BREAK

1:00–1:25 — A SOLO PR, THEN A FORK CONTRIBUTION (first guide, part 4)

Create add-question from updated main. Add question.md, save, inspect, commit.
With no uncommitted changes, switch to main: the file is absent. Switch back.
Publish the branch and create a PR with main as base. Show Files changed.

Each student opens, inspects, and merges their OWN practice PR on GitHub.
No partner is needed. Return to main in Desktop and pull; check the file locally.
Explain that Merge pull request accepts the change, while Close pull request
alone closes the proposal without merging it.

Next, use the browser to fork the teaching repo, create clarify-instructions,
and improve one Markdown passage. Open a PR from the student's fork and branch
to macss-berkeley/compss-211a, base main. Show the D-Lab/Tom comparison screenshot
HERE to explain PRs between repositories. The instructor reviews and can merge
one ready contribution. Other PRs can stay open for later review.

1:25–1:55 — TEAM COLLABORATION (2_project_repo.md, sections 1–4)

Use an existing team repo, or have ONE teammate create it from the project
template. Invite collaborators; everyone accepts and clones that same repo.
Check the shared URL and the repository selected in Desktop.

Each student starts from updated main, creates plan-USERNAME, adds their own
plan-USERNAME.md with a question/source/next step, commits, and opens a PR.
A teammate reviews and merges. Everyone returns to main and pulls, then opens
a teammate's note locally. A tentative project idea is enough.

Then create the deliberate two-PR conflict. Add and merge team-next-step.md
with the starting sentence. Both teammates pull it and branch before either
changes main. A uses check-license; B uses compare-sources. Both change the
same line differently, commit, publish, and open PRs. B reviews and merges A's
PR; B's PR now conflicts. B resolves it on GitHub and selects Commit merge,
which updates B's branch. A reviews the result and selects Merge pull request
to bring it into main. Everyone pulls the agreed sentence locally.

Mention one active editor per notebook and inspecting which files are included
in commits. Point to .gitignore's limits: it does not erase tracked history.

1:55–2:00 — CLOSE

Ask students to show a branch commit, a reviewed PR, and a teammate's merged
note locally. Agree on one next real project task and a new branch for it.

Sections 5–7 of the team lesson are follow-up: environment, notebooks/scripts,
and project agreements before Friday. SSH and Pages remain optional reference.

IF TIME IS TIGHT

Demonstrate the stash/conflict sequence once if students need more setup time;
they can repeat it after class. Finish course-improvement PRs after class too.
Protect time for the team repo: complete one reviewed contribution per team.
Demonstrate the two-PR conflict with two students if necessary; other teams can
repeat it after class. Finish remaining planning-note PRs afterwards.
